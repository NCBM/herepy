# 16. Wine builds and smokes the Windows runtime; it does not decide whether Windows ships

**Status**: accepted, 2026-11-16.

## Context

ADR 0015 makes a target's boot the release gate and admits the consequence: only Linux x86_64 can be booted
here, so five targets are plans. It also assumed the Windows half of the work was out of reach on this
machine, because a CPython extension for Windows is compiled with MSVC and links `libs/python313.lib`.

That assumption was wrong, and the machine says so. Three measurements, in the order they mattered:

- Wine 11.21 runs the pinned Windows CPython: `wine python.exe -c ...` answered
  `3.13.18 AMD64 Z:\…\win\python`, with no `winetricks` recipe — the artifact carries its own
  `vcruntime140*.dll`. The pinned `cp313-win_amd64` numpy wheel imports in the same interpreter
  (`numpy 2.5.5`), and a `.pyd` compiled against the artifact's `include/` and `libs/python313.lib` imports
  there too.
- `/opt/msvc` is **msvc-wine**: the real MSVC 14.51 toolchain running under Wine behind wrapper scripts. So
  `cl` is available on Linux, with the compiler family the interpreter itself was built with.
- The Windows JDK runs under Wine, and jep builds and works there. Compiling the jep 4.4.0 sdist's 75 C files
  with one `cl /LD` (JNI headers generated by `javac -h` from the sdist's Java sources, linking `jvm.lib` and
  `python313.lib`) produced a 321 KB `jep.pyd`; a 25-line Java probe loaded it in a Windows JVM 21 under Wine,
  started the artifact's CPython and printed
  `python : 3.13.18` / `prefix : Z:\…\win\python` / `numpy : 2.5.5` / `sum : 45.0` / `probe ok`.
  That is the entire Java→Python path for the Windows target, minus the game.

## Decision

**Wine with msvc-wine is the Windows target's build and smoke environment, and nothing more than that.**

- The Windows artifacts are **built here**: base runtime from the pinned asset, numpy from the pinned wheel,
  and jep compiled from its pinned sdist with `cl` against that runtime's headers and import library.
- jep's Windows build is a **direct `cl` invocation**, not `pip install jep`. Its build drives MSVC discovery
  through distutils and the registry, which Wine does not provide usefully; the sources are 75 `.c` files and
  the recipe is one command line, which is also easier to pin.
- The smoke test is the probe above: a Windows JVM under Wine loads jep, starts the runtime, imports numpy and
  computes something. It covers the DLL search, the ABI, the interpreter's own startup and the pack path —
  everything `runClient` covers except the game.
- **The boot gate stands.** A target that has only passed the Wine smoke is "runtime verified", not "booted",
  and ADR 0015's rule is unchanged: it does not ship. Wine is not Windows — it has no GPU stack worth trusting
  for Minecraft and no registry — so passing it cannot stand in for a release check.
- jep has one native binary under two names (`jep.pyd` for CPython, `jep.dll` for `System.load`). Java-side
  naming is the mod's to fix: `PythonManager.getJepLibPath()` asked for `libjep.pyd` on Windows, which is
  neither of jep's names, and the probe had to load `jep.dll` itself — done, see below.

## Consequences

- The Windows target moves from "nothing verified" to "runtime verified" without a Windows machine, which is
  the largest single step available from here. What remains unverified is the game, and that has to happen on
  Windows.
- Building Windows artifacts no longer needs a Windows runner: a Linux runner with msvc-wine can do it, so
  ADR 0015's matrix row for `windows-x86_64` is about testing, not building.
- The smoke harness needs a Windows JDK (~190 MB, unpacked once) and a probe class; both belong in the repo
  as a task (`wineJepSmoke -PwinJdk=…`) rather than in someone's shell history.
- Windows-side work acquires a fast loop: the smoke runs in seconds under Wine, where the game takes minutes
  and needs a person. The Windows removal list can therefore be measured the same way the POSIX one was —
  remove, smoke, read the log — before anyone touches a Windows machine.
- A wart to keep an eye on: compiling all 75 sources in one directory makes MSVC warn `LNK4042` about a
  duplicate `JPyCallable.obj`, which means two `.c` files with the same basename collide. The probe passing
  does not prove nothing was dropped; the build should give each source its own object path.

## Alternatives considered

- **Wait for a Windows machine.** Honest and slow, and it leaves the whole Windows path unexercised until
  someone has the hardware — including the parts that have nothing to do with Windows.
- **Cross-compile jep with mingw-w64.** It is installed and it can link `python313.lib`, but it is not the
  toolchain the interpreter was built with. MSVC is here and is, so the choice is not close.
- **`pip install jep` under Wine.** The path distutils takes to find MSVC is registry-shaped, and Wine's
  registry is not a Visual Studio installation.
- **Use Wine to run Minecraft and call that the boot.** It would be the most convincing-looking thing to do
  and the least meaningful: a GPU stack and a registry translated by Wine are not the platform we ship to.
- **Skip the JDK and test only the Python side.** The Python side alone cannot answer whether `libjep` loads
  in a JVM, which is the question the whole embedding depends on.

## Carried out, 2026-11-16

Everything above was measured in this session, in a scratch directory, and nothing of it is in the repository
yet: the Windows runtime tree, the `cl` build of jep, the JDK, the probe, and the smoke run. The recipe is:

```
javac -h build/include -cp jep.jar -d /tmp/out $(find src/main/java -name '*.java')
cl /LD /O2 /DPACKAGE=jep /DJEP_NUMPY_ENABLED=1 /DWIN32=1 /D_CRT_SECURE_NO_WARNINGS=1 \
   /I<jdk>/include /I<jdk>/include/win32 /I<runtime>/include /Ibuild/include /Isrc/main/c/Include \
   /I<runtime>/Lib/site-packages/numpy/_core/include \
   /Fe:<runtime>/Lib/site-packages/jep/jep.pyd $(find src/main/c -name '*.c') \
   /link /LIBPATH:<jdk>/lib jvm.lib /LIBPATH:<runtime>/libs python313.lib
wine <jdk>/bin/java.exe -cp <probe>;<jep.jar> Probe <jep.dll> <runtime> <runtime>/python313.dll
```

What this record owes:

- The harness in the repository: **done** — `./gradlew wineJepSmoke -PwinJdk=<unpacked JDK>` builds the Windows
  runtime, numpy and jep from the pins and runs [`tools/wine/JepProbe.java`](../tools/wine/JepProbe.java) under
  Wine. `-Ppackage` builds the shape that ships — removals applied and the tree precompiled — and
  `./gradlew packageWindowsRuntime` archives that tree (§0015).
- The Windows removal list, measured with that harness the way the POSIX one was: **done**, and the probe stayed
  green (§0015).
- The `libjep.pyd`/`jep.dll` naming decision on the Java side, and a Windows-shaped `PythonManager` for the
  layout ADR 0015 measured: **done**. `PythonManager` no longer asks `os.name` where the runtime's files are, it
  asks the tree — `python.exe` or `Lib/` is the Windows layout — and then names each file the way that layout
  does: `jep.dll` for the JVM to load, `libjep.so`/`libjep.dylib` elsewhere, and the interpreter's own
  `python313.dll` or `libpython3.13.so.1.0` the same way. Run under a Windows JVM in Wine against
  `build/windows-x86_64/runtime` it answered `Lib`, `jep.dll` and `python313.dll`; the same class then booted
  the dev client unchanged (`Python 3.13.18`, the stub generator's `3900 ok, 83 failed`).
- A real Windows boot before Windows is called supported.
